# Architecture

Each choice lists its justification and at least one rejected alternative with the reason. Seeded from the `migration-engine` design ("Key Decisions") and `.kiro/steering/decisions.md`.

## Overview

```text
client_app ──> Orchestrator :8000 ──(phase 1-3)──> Legacy_A_API :8001   (raw CSV, read only)
                    │        └──(phase 4)───────> Target_API   :8003   (Target_DB, read only)
                    └──────────────────────────> Legacy_B_API :8002   (own format, all phases)
Migration_Pipeline (LangGraph Run_Workflow) ──> rules/ (pure) ──> Target_Repository ──> var/target.db
                    ├─> LLM_Client (only LLM caller) + Resolution_Cache
                    ├─> HITL_Queue + Human_Decision_Store
                    └─> Decision_Logger, Report_Generator ──> var/ops.db
```

## Choices

| Choice | Justification | Rejected alternative and reason |
|---|---|---|
| **Strangler Fig in 4 phases, enforced by the Phase_Controller and routed by the Orchestrator** | The phase only changes routing; every request reads the phase once and finishes on that backend, so a switch never interrupts a client. Forward moves go one phase at a time; phase 4 needs a gate (zero open questions, zero Gap on the Control_Sample) and an explicit human approval that also validates the coverage and exclusion summary. Operators can roll back 4 -> 3 (only if Legacy A is reachable) and 3 -> 2; rollbacks are logged like other transitions. | Big-bang cutover: one failed load means an outage for the client. Free phase jumps: phase 4 could be reached without reconciliation. |
| **Same client answer before and after cutover** | In phases 1-3 the Orchestrator returns the expected records (Legacy A rows passed through `decide_row`, MIGRATE and CORRECT only), exactly what phase 4 reads from the Target_DB. The Client_App checks availability and functional parity separately on fixed control VINs. | Raw Legacy A rows in phases 1-3: the response would change shape at cutover, so parity could not be measured. |
| **Rule_Engine as pure functions configured by Rule_Config** | `rules/` takes one raw row and a read-only `RuleContext`, performs no I/O and returns Field_Decisions in a fixed order. Dictionaries, mappings, threshold, batch size, Legacy B switch and the auto-apply allow-list live in YAML under `rules/config/`. Identical inputs give identical decisions (tested), and field-local work is memoized once per distinct value. | Rules mixed with pipeline code or DB queries: not reproducible, not testable in isolation. Rules hard-coded: every dictionary change needs a release. |
| **LLM_Client as the only LLM caller, with the Resolution_Cache and the Confidence_Threshold** | One metered entry point counts tokens per call and per Run and never logs the key. The Resolver_Agent sees one Unknown_Variant Pattern_Key at a time (field, reason, normalized value, allowed values), its answer passes a deterministic validator, and only closed-dictionary fields (originTool, ecuName, Vehmodel, ecuCode) are auto-applied at or above 0.9. Applied proposals are cached by Pattern_Key, so a pattern never costs tokens twice. | One LLM call per row: cost grows with rows (the brief targets ~1,200 tokens per 100k records) and results are not reproducible. Auto-applying dates, ValueReference or ids: an LLM guess would become data without human review. |
| **Multi-provider LLM_Client: local Ollama by default, Anthropic optional** | `llm.provider` in Rule_Config selects `ollama` (default, `qwen2.5:7b` on `http://localhost:11434`) or `anthropic`; the rest of the code keeps the same three calls (`is_available`, `complete`, `totals`). Ollama is called over plain HTTP (`POST /api/chat`, `"format": "json"`, temperature 0), tokens come from `prompt_eval_count` and `eval_count` and are recorded like Anthropic tokens, and the cost is 0 €. A local model needs no key, keeps the data on the laptop and keeps working without Internet during the demo; Anthropic stays one config line away. Requests carry `keep_alive: 2h`, the timeout is 180 s, `start_all.ps1` warms the model up, and the availability check loads the model so a load failure (Ollama's message kept) switches the Run to Degraded_Mode at its start. | Anthropic only: the demo depends on a key and a network, and every call costs money. A generic framework (LangChain chat models, LiteLLM): one more dependency and abstraction layer for two providers and three calls. |
| **Resolver_Agent with read-only tools and a provider-neutral JSON protocol** | The agent may call `lookup_dictionary`, `find_similar_values`, `inspect_pattern_frequency` and `test_proposed_rule`, which read Rule_Config and aggregate counts of the Run and write nothing. Each turn the model answers one JSON object, `{"tool": ..., "args": ...}` or `{"final": {...}}`, at most 3 turns per Pattern_Key. Every tool call is logged with its parameters and a summarized result (`decision_tool_call`, `GET /ops/runs/{run_id}/tool-calls`) and summarized in the explanation of the Decision_Records it supports. With `qwen2.5:7b`, 18 of 18 answers followed the protocol (see `docs/lessons-learnt.md`). | Provider-specific tool calling (Anthropic `tools`, Ollama `tools`): two formats to maintain, and small local models follow it less reliably than a forced JSON answer. An unbounded agent loop: unpredictable cost and latency. |
| **Question_Advisor: an agent that advises the human, never decides** | On request ("Demander l'avis de l'agent", `POST /ops/questions/{id}/advise`, a background job), the agent investigates one open question with read-only tools (group rows, other rows of the same VIN, Legacy B model, value distribution of the field, deterministic test of an option) through the same JSON protocol as the Resolver_Agent, 4 turns at most. It returns an option among those offered, a justification, a confidence, the evidence and what it cannot know. Deterministic checks refuse an option that is not offered, a value outside the allowed values, a value no tool returned, and any value for dates, tools, versions or identifiers. The advice, its tool calls and its tokens are stored (`question_advice`, `question_advice_tool_call`, `llm_call` with purpose `question_advisor`) and shown in the question; the human still answers. | Letting the agent answer the questions: decisions.md keeps dates, ValueReference and identifiers for humans, and a grouped answer changes many rows at once. No agent at all: the human has to search the source rows and Legacy B by hand. |
| **Human_Questions grouped by Pattern_Key** | Keys are broad (field + reason, plus the Label_Template for unreadable ecuCode), giving 12 questions on the 10,000-row file. A question keeps its own `question_id`, scope (group or row) and status; "case by case" creates one row question per member. "Apply a value to the group" is offered only for homogeneous groups (same raw value and label), and never for R6, R7 or the empty R8 fields. Decisions are persisted outside the LangGraph checkpoints and reapplied as rules in later Runs (row-scoped decisions only to their row). | One question per raw value or per row: hundreds of questions. Applying one value to a mixed group: a wrong value would be spread over unrelated rows. |
| **Degraded_Mode** | Decided once at Run start when the chosen provider cannot be used: Ollama unreachable or model not pulled, no `ANTHROPIC_API_KEY` for anthropic, or `--no-llm`. The reason is written in the end-of-run report. The Run still applies rules, Human_Decisions and cached resolutions, with the same decisions; Unknown_Variants go to humans with a Degraded_Mode explanation; schema discovery proposes the reference Column_Mapping. All runs in `docs/cost-performance.md` ran in this mode. | Failing the Run without an LLM: the demo and the migration would depend on a provider. |
| **LangGraph only for the Run_Workflow, nodes per batch or per Pattern_Key** | Native pause (`interrupt()`) after the report when questions are open, resume with `Command(resume=...)`, checkpoints in SQLite (`var/checkpoints.db`). The checkpoint holds only ids and small lists; rows, memo and decisions stay in a process-local RunStore. A resume starts a new Run with a new run_id. | A node per row: 10,000 checkpoints per Run. A hand-written state machine: no durable pause point. |
| **Idempotent load: upsert keyed by diagnosticOpID, UUID v5 for missing ids** | `INSERT ... ON CONFLICT DO UPDATE` in dependency order, one transaction per batch, then one transaction per row on failure (the failing row becomes REJECT `LOAD` with the constraint name). Generated ids are UUID v5 over the canonical JSON of the Operation_Identity, which also includes DiagToolName and DiagToolVersion. A second Run gives the same table counts (tested). | Random UUID4: duplicates on every Run. Deleting and reloading: breaks continuity and loses earlier rows. |
| **Constraints in the database** | Named CHECK constraints (VIN format, dictionaries, ValueDescription, ValueReference format) use `regexp_match()` plus `length()`, with portable types; foreign keys are on for every connection. | Validation in Python only: invalid data could still be written by another path. GLOB-only CHECKs: less readable, and the team kept `regexp_match()`. |
| **Three SQLite files** (`target.db`, `ops.db`, `checkpoints.db`) | The target is the "new system" and can be replaced alone; the read-only Target_API cannot see operational tables; checkpoints can be deleted without losing Human_Decisions. | One database: the target would carry operational tables. PostgreSQL in Docker: setup cost in a 48 h hackathon. |
| **Background jobs for the long operations** | Starting a campaign, resuming it, schema discovery and the Question_Advisor can take minutes with a local model, longer than an HTTP timeout. `POST /ops/jobs/...` answers 202 at once with a Job; the UI polls `GET /ops/jobs/{job_id}` every 3 s, shows "en cours" and disables the buttons. Two lanes (`pipeline`, `llm`) run one job at a time each, so two Runs never share the Run_Workflow, and a job whose key is already queued or running is refused with 409. Jobs live in memory; the Runs they start are persisted as before. The synchronous routes stay for scripts and tests. | Synchronous routes with a longer timeout: the browser and Streamlit still wait minutes and a reload loses the answer. A task queue (Celery, RQ): a broker to install for one Orchestrator process. |
| **Query_Agent (bonus chat): the LLM writes SQL, deterministic code decides whether it runs** | A LangGraph graph of four steps: check the question (1 to 1,000 characters, provider available), generate one SELECT through the LLM_Client (schema and closed values in the prompt), validate it with `sqlglot` (it parses, exactly one statement, SELECT or set operation only, no write node inside, every table in the allow-list of Rule_Config, CTE names excepted, no schema other than `main`), then execute it on `file:target.db?mode=ro` with a `sqlite3` authorizer (SELECT and reads of allowed tables only), a 10 s progress-handler timeout and the row limit. A failed step returns an error naming the step, and the SQL never runs. The route is synchronous (one question, a few seconds) and its tokens go to the cost report under "chat (Query_Agent)". | Executing the model's SQL with a regex filter: easy to bypass (comments, CTEs, nested statements). A read-only database user: SQLite has none; the `mode=ro` connection plus the authorizer give the same guarantee. Letting the model answer from memory: no evidence and invented numbers. |
| **Legacy B as a chat consumer** | Legacy B is a system, not a person, so its agent (`agents/legacy_b_asker.py`, `scripts/legacy_b_asks.ps1`) writes three questions from a summary of its own records (fixed questions when no LLM answers), sends them to `POST /ops/chat` with `consumer: "legacy_b"` and compares the returned VIN/model rows with its own models. The chat page can launch it with a button, still as a separate process (`ui/legacy_b_runner.py`), so the demo needs no terminal. It goes through the same validation, read-only connection and row limit as the UI; its calls are metered with run_id `legacy-b`. | A dedicated Legacy B data route: one more contract to freeze for a bonus. Questions written by hand only: it would not show a system using the chat by itself. |
| **One FastAPI app per service** | Legacy A can be stopped to show retirement, the 503 path and the refused rollback, without stopping the Orchestrator. | One app with routers: a "down" backend cannot be shown. |
| **CSV read with the stdlib `csv` module** | Cells stay exact strings; a row whose cell count differs from the header is flagged and rejected `INGEST MALFORMED_ROW`. | `pandas.read_csv`: pads short rows silently, so malformed rows would be hidden. |
| **Legacy B lookup before asking a human** | An unreadable Vehmodel with no unique model on other rows of the VIN takes the Legacy B model (CORRECT, Legacy B named). A Legacy B model different from the decided model is an R7 question. If one VIN lookup fails, the whole index is emptied for the Run. | Asking a human directly: more questions for data another system already holds. A partial index after a failure: results would depend on which VINs failed. |
| **Reconciliation by diagnosticOpID** | Records are matched by id, then values are compared; gaps are counted as missing_in_target, unexpected_in_target, value_mismatch and duplicate_in_target. Each Gap triggers one reload Run of its rows, then one re-compare; a remaining Gap becomes one `_row|RECON_GAP|...` question. A VIN that cannot be read is "not performed" and fails the gate. | Matching by Operation_Identity only: a changed id would look like one missing and one extra record without explanation. |
